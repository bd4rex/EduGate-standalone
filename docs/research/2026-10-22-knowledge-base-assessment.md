# EduGate 知识库有效性与升级方案研究

研究日期：2026-10-22（Asia/Shanghai）。适用范围：**单教师、多个班，长期积累大量教材资料**；这是本次用户明确选择的场景。多个班的资料积累与同一时刻的学生并发需要分别评估。

## 结论与建议

当前知识库已经实现资料导入、切片、检索和辅助回答，属于基础的关键词式 RAG。少量、整理过的课堂资料和含明确术语的问题可以使用，但目前没有充分证据支持把它当作长期教材库的可靠问答方案。样例中已复现漏检、误检和长问题丢失关键术语；“严格模式”也没有形成可靠的证据门槛。

建议保留 EduGate 的单教师界面、课堂控制、模型接入和本地存储，升级资料处理与检索模块。优先路线是：**课程范围过滤 + 中文关键词检索 + 语义检索 + 章节上下文 + 可核验引用**。重排序通过对照试验决定是否默认开启。向量数据库本身不能解决抽字错误、教材版本混用或答案没有依据的问题。

落地时先补严格模式、中文查询处理和检索观测，再比较 BM25 与混合检索。嵌入式检索引擎优先评估 LanceDB；SQLite FTS5 是较小改动的关键词升级方案。暂不把完整 Dify、RAGFlow 或 GraphRAG 平台作为单机版的必需依赖。如果真实资料以扫描教材、复杂表格和图形题为主，文档解析与原页保留应提高优先级。

以上是工程选型建议，**尚未实施升级，也未证明任何候选方案在本项目上已经达到目标效果**。

## 当前实现到底做了什么

| 环节 | 当前行为 | 对本场景的意义 |
|---|---|---|
| 管理 | 多个知识库来源，每个教学场景绑定一个 `knowledge_source_id` | 可以按课程手动分库；缺少教材版本、章节、适用年级等细粒度筛选 |
| 导入 | 文本、Markdown、HTML、CSV、JSON、XML、日志和 PDF；上传与目录扫描 | 目录扫描能按哈希更新、识别删除；没有 Word/PPT 专用解析和 OCR |
| 限制 | 默认每文件 25 MiB，PDF 最多 200 页 | 整本长教材可能被拒绝；扫描 PDF 可能抽不到文字 |
| 切片 | 压平空白，每段 900 字符，重叠 120 字符 | 段落、章节和页码定位丢失；可能截断题干、条件、表格或代码 |
| 查询 | 只用最后一条用户消息；中文连续串及 2/3/4 字组合，英文数字词；最多 40 个词项 | 不理解同义改写；追问缺少前文；按长度截断可能丢掉短而关键的术语 |
| 排序 | 取出当前来源全部片段，以 `sum(text.count(term))` 排序，默认取 5 段 | 没有倒排检索、BM25、向量、词稀有度或可信度门槛；文件名不参与匹配 |
| 回答 | 将片段和文件名加入模型提示词 | 有基础来源提示，但没有结构化页码引用、证据充足性判定和引用核验 |
| 观测 | 请求日志记录来源 ID、用量和耗时等 | 尚无命中片段、排序分数、拒答原因、检索阶段耗时等完整评估链路 |

## 已复现的问题

### 检索行为

| 输入 | 当前返回 | 可以支持的结论 |
|---|---|---|
| 什么是 IP 地址／IPv6 是多少位／NAT 有什么作用 | 有相关片段 | 明确术语查询可以工作 |
| 我家几台电脑怎样共用一个外网号码？ | 0 个片段 | 与 NAT 内容接近的口语表达漏检；这条不是完整答案正确性的金标准 |
| 你能再举个例子吗？ | 0 个片段 | 仅检索最后一句不能处理这类依赖前文的追问 |
| NAT 是谁发明的？ | 3 个片段，仅因 NAT 命中 | 样例没有发明者信息，“命中”不代表具有回答依据 |
| 网络游戏充值怎么操作？ | 3 个片段，主要因为“网络” | 无关问题也可能被判为检索命中 |
| 一大段礼貌铺垫后询问 NAT | 词项达到 40 个，NAT 被舍弃，0 个片段 | 查询截断策略会丢失真正的问题关键词 |
| 文件名为“量化.md”，正文只解释概念，查询“量化” | 0 个片段 | 文件标题没有纳入检索 |

这是诊断样例，不是随机抽样的准确率评测。未来算法应使用独立的教学问题集验证，不能只针对这些示例修补。

### 严格模式的可靠性

`_strict_miss_decision()` 只在“没有任何关键词命中”时进入话题判断。一旦误匹配到“网络”等片段，就没有这一层拦截。没有命中时，又可能让模型根据知识库名称、文件名清单判断 RELATED，随后在没有教材片段的情况下继续调用回答模型。

虽然提示词要求不足时不使用外部知识，但同时允许“围绕该主题继续回答”；这不能保证界面所说的“仅根据课堂知识库回答”。本次确认的是代码路径和提示词冲突，没有调用真实模型证明它必然编造答案。

建议拆成两种清晰的教学策略：

- **资料依据模式**：有支持当前问题的证据才生成事实性答案；证据不足就说明缺口、询问范围或请教师补充资料。引用必须映射到真实文件和页码/章节。
- **主题辅助模式**：允许通用知识辅助解释，但明确区分教材依据与补充说明；话题相关不能冒充教材有证据。

### 规模与响应时间

首次本机探针结果如下；保存脚本的再次执行见 JSON，计时会随机器负载波动。

| 当前来源内的片段数 | 4 次顺序检索的中位耗时 |
|---:|---:|
| 1,000 | 44 ms |
| 10,000 | 416 ms |
| 30,000 | 1,254 ms |

测试用重复的样例片段，属于受控合成负载；不是完整教材库，不含模型、网络、OCR、建库或多学生并发。不能据此宣称支持某个学生人数，也不应把片段数直接换算成教材本数。

代码每次在 Python 中遍历片段，耗时随数据增长。聊天异步路径直接执行这个同步检索；严格模式的检查和组装上下文可能重复检索。`get_source()` 还通过所有来源的聚合列表定位单一来源。建议使用索引、一次请求复用检索结果、避免阻塞事件循环，并针对实际教师电脑测班级集中提问时的延迟。

## 技术路线与取舍

以下整合用户提供的研究讨论，并结合本项目实测作出取舍。“推荐”指下一步验证顺序，不代表已经完成性能或效果验收。

| 路线 | 适用处 | 局限与本项目取舍 |
|---|---|---|
| 全文上下文 | 一课少量讲义、实验步骤；可做回答效果基准 | 输入量、模型费用与首字时间需测；放得下不等于能准确使用全部内容，不适合每次塞入长期总库 |
| 中文关键词 + BM25 | 术语、题号、IP、代码、文件名；低成本升级 | 同义表达仍可能漏检，适合作为基线和混合检索的一路 |
| 向量语义检索 | 学生口语化、概念描述、同义表达 | 相似不等于可回答，精确编号和条件仍需要关键词；需要单独选择 Embedding 模型 |
| 混合检索 | 长期多教材、多种提问方式 | 推荐主路线；关键词与向量召回后融合，按实测决定是否增加重排序 |
| 章节/树结构检索 | 整本教材、章节联系和前置知识 | 优先保存章节元数据与父子段落；PageIndex 的模型沿树推理作为可选对照，不先让每个学生问题都触发多轮模型调用 |
| 知识图谱/GraphRAG | 跨材料关系、主题归纳、综合研究问题 | 抽取、核验和更新成本更高；普通课堂问答暂不作为首选 |

全文上下文的取舍须在当前所用模型上重新实测；[Lost in the Middle](https://arxiv.org/abs/2307.03172) 是历史研究证据，不能当作所有 2026 年模型的统一性能结论。[SQLite FTS5](https://sqlite.org/fts5.html) 提供全文索引和 BM25，但默认 `unicode61` 按连续字符划词，不能直接当成中文分词器；本次也复现了默认配置查不到“子网掩码”的情况。不能只换 SQL 接口就宣称改善中文效果。

[PageIndex 官方介绍](https://docs.pageindex.ai/)描述了文档树索引和基于模型推理的树检索。[Microsoft GraphRAG](https://microsoft.github.io/graphrag/)则包含实体关系抽取、社区层级和摘要。两者解决的问题与成本不同，不应混为“加个向量库”。

Embedding 负责把内容变为可检索表示，文档通常在导入时计算并复用；重排序重新比较问题与候选片段；回答模型负责根据证据组织答案。这三种角色可以使用不同模型，当前聊天供应商能回答并不代表其接口也支持 Embedding。

Agentic RAG 是查询改写、问题分解和多轮查证的编排方式，可以叠加在不同检索路线之上。对课堂建议限制轮次与预算，先解决普通检索问题。多模态处理则是另一个维度：[ColPali 论文](https://arxiv.org/abs/2407.01449)研究直接检索页面图像；在本项目应先保留原页、补 OCR 和版面解析，再对图表、公式或几何题验证视觉检索的额外价值。微调改变模型参数，不是本次教材版本管理和可追溯引用的优先解法。

## 部署方案比较

| 方案 | 对 EduGate 的适合度 | 建议 |
|---|---|---|
| 保留当前实现 | 适合少量临时资料，长期教材库不足 | 可继续作为回归基线，不宜直接扩大总库依赖 |
| SQLite + 中文处理 + FTS5/BM25 | 延续现有依赖，改动较小 | 第一阶段或低资源回退方案，必须验证中文词语、英文术语和数字查询 |
| SQLite 管理业务 + LanceDB 本地检索 | 保留单机操作方式，同时支持向量、全文和过滤 | 优先做混合检索原型；验证 Windows、macOS 打包、模型/分词资源、备份与升级迁移 |
| 独立 Qdrant 服务 | 检索服务与应用可以分离 | 有独立服务器、共享服务或单机资源不足时再评估；不因“用了向量”就默认增加服务器 |
| Dify | 有知识库管理、检索测试、引用及应用编排功能 | 愿意维护独立平台时可选；当前教师端功能已有较多重叠 |
| RAGFlow | 面向复杂资料解析与可追溯检索 | 扫描教材/复杂文档为主且愿意配置独立服务时值得专项试验 |

[LanceDB 官方文档](https://docs.lancedb.com/)将 OSS 定位为嵌入式检索库；[混合检索文档](https://docs.lancedb.com/search/hybrid-search)支持关键词与向量融合、过滤及重排序。[全文检索文档](https://docs.lancedb.com/search/full-text-search)说明了中文 Jieba 与多语言 ICU 选项；分词资源及实际版本应随打包验证。这些是能力依据，尚非本项目上的效果对比结果。

[Qdrant 官方快速入门](https://qdrant.tech/documentation/quickstart/)可作为独立部署候选，客户端本地模式另有 [官方实现与适用说明](https://github.com/qdrant/qdrant-client/blob/master/qdrant_client/local/qdrant_local.py)；本地模式的存在不等于任意数据量和并发都适用。

[Dify 的知识库集成文档](https://docs.dify.ai/en/cloud/use-dify/knowledge/integrate-knowledge-within-application)包含元数据过滤、检索设置与引用；其 [Docker 部署文档](https://docs.dify.ai/en/self-host/deploy/quick-start/docker-compose)在 Windows 上要求 WSL 2 与 Docker Desktop。对当前单机分发方式，这会增加安装与维护步骤。

[RAGFlow 官方仓库](https://github.com/infiniflow/ragflow)列出 Word、PPT、扫描件等输入以及可追溯引用，当前推荐起始配置为 4 核、16 GB 内存、50 GB 可用磁盘，实际需求另受解析、模型和并发影响。该资源开销是其更适合独立服务评估的原因之一。

## 面向多班长期使用的具体设计

1. **分开“资料总库”和“课堂资料范围”。** 教材长期保留，按学科、年级、教材版本、学期、章节标记；不同班级复用同一份资料，通过课堂集合选择使用范围，不按班重复复制全文。当前课堂只检索教师指定内容，并可明确扩大范围。
2. **先把教材正确读出来。** 保存文件版本、页码、标题路径、段落与原页定位；表格、题干和答案尽量保持逻辑完整。教师解析预览明确显示可检索、抽取失败和需要 OCR 的页。教师参考答案与学生可用资料应分区，不能只靠提示词隐藏答案。
3. **改善查询与候选选择。** 标题/章节参加检索；保护 IP、术语和代码；追问可结合最近有效问题做有限改写。关键词和向量分别取候选，做去重与融合，再按 token 预算选择证据。不要把同一段的重叠切片当成多份独立支持。
4. **保留章节上下文。** 小片段用于定位，必要时补父段落或相邻段；不用固定字符切片独自承担长教材理解。页码和版本必须跟随证据传到答案引用。
5. **建立证据门槛。** 明确资料依据模式与主题辅助模式；低证据不生成确定事实。引用既要指向真实页面，也要人工抽查其是否支持答案中的断言。
6. **把导入和课堂请求分开。** 建库、OCR、向量化放后台任务；索引按文件哈希和模型版本增量更新，变更后使相关缓存失效。新索引完成后再切换，避免半更新状态影响课堂；旧版本可恢复。
7. **维持普通教师的操作成本。** 课堂界面仍围绕“上传资料、选教材/章节、试问、开始课堂”；索引和模型参数放在高级设置。资料和索引本地保存，Embedding 可选本地或 API。使用云端 Embedding 时相应资料会发给供应商；云端回答模型仍会收到选中的片段，本地索引不等于全流程离线。

## 如何判断升级是否有效

先从实际使用的教材抽取约 80—120 个教师审定问题，分别覆盖原词、口语改写、精确编号、连续追问、跨章节、无答案、错误前提、版本冲突和图表题。每题标注允许的教材版本、可支持答案的原文和页码，保留一部分问题作未调参的验收集。

用同一语料、问题、课堂范围、回答模型和上下文预算比较：现有方案、中文 BM25、纯向量、混合检索、混合加重排序；少量讲义再加入全文上下文基准。分别记录检索和最终回答，避免更强回答模型掩盖检索缺陷。

建议观察以下指标，数值目标是**初始验收建议，不是已取得的成绩**：

| 指标 | 建议起点与解释 |
|---|---|
| 可回答问题的证据召回 | 前 5 个候选包含教师认可的支持证据，争取达到 90% 以上，并单列口语与追问题 |
| 无答案处理 | 无资料依据的问题正确说明不足，争取达到 95% 以上；统计误拒答，不能靠全部拒答达标 |
| 引用 | 引用定位应全部可打开；人工评审答案断言是否被引用支持，另报支持率 |
| 课堂范围与版本 | 不越过教师选定范围，不把不同教材版本混用；这些是必须检查的约束 |
| 性能 | 记录检索、重排序、首字与完成耗时的 P50/P95，以及排队、失败与费用；目标按实际机器和课堂节奏制定 |
| 更新 | 更新、删除、重启、备份恢复后抽查索引一致，失败时不能悄悄继续当作新版本 |
