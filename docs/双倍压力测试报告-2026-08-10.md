# 双倍压力测试报告

**中文** · [English](Double-Load-Test-Report-2026-08-10.md) · [返回项目首页](../README.md)

测试日期：2026-08-10

## 结论

EduGate 使用默认 **16 路模型并发**承受了原测试两倍的课堂负载。快速模型和 750 ms 慢模型的最终测试均为 34/34 项检查通过，没有 429、500、连接失败、SQLite locked、日志丢弃或写入失败。

双倍负载下核心吞吐基本保持不变，说明服务没有发生容量塌陷；P95 延迟上升主要来自 128 个学生共享固定的 16 个上游槽位。64 人仍是推荐课堂规模，128 人属于稳定性余量测试，不代表相同延迟目标。

## 默认配置确认

本轮没有通过环境变量指定 `MODEL_MAX_CONCURRENCY`，实际使用项目默认值。以下位置均为 16：

- 后端运行默认值
- 系统高级设置默认值
- 新安装的 `.env.example`
- 本机便携版 `config/edugate.env`

## 测试环境与口径

- Windows 10.0.19045
- Intel Core i7-8700，12 个逻辑处理器
- 31.83 GB 物理内存
- EduGate 和伪 OpenAI 兼容模型均运行在本机回环网络
- Python 执行池保持 4 路、候位队列 64
- SQLite 异步写队列 4,096、批量 100
- 课堂记录和技术请求日志均开启

原测试与双倍测试：

| 阶段 | 原测试 | 双倍测试 |
|---|---:|---:|
| 学生同时加入 | 64 | 128 |
| 健康检查 | 512，客户端并发 64 | 1,024，客户端并发 128 |
| 普通聊天突发 | 64，并发 64 | 128，并发 128 |
| 持续聊天 | 256，并发 64 | 512，并发 128 |
| 流式聊天 | 64，并发 64 | 128，并发 128 |
| Python 任务 | 64 | 128，总量翻倍、同时在途保持 64 |

Python 同时在途保持 64，是为了测试双倍任务量而不故意突破默认 64 长度候位队列。另行测试 128 个 Python 同时提交会触发有界队列保护，不属于本报告的全成功口径。

## 75 ms 快速模型

| 阶段 | 64 人吞吐 | 128 人吞吐 | 64 人 P95 | 128 人 P95 | 结果 |
|---|---:|---:|---:|---:|---|
| 学生加入 | 105.31 req/s | 90.47 req/s | 0.51 s | 1.27 s | 128/128 成功 |
| 健康检查 | 88.05 req/s | 77.35 req/s | 1.83 s | 4.35 s | 1,024/1,024 成功 |
| 聊天突发 | 55.24 req/s | 55.80 req/s | 1.04 s | 2.12 s | 128/128 成功 |
| 持续聊天 | 52.25 req/s | 51.83 req/s | 2.66 s | 6.51 s | 512/512 成功 |
| 流式聊天 | 48.71 req/s | 47.01 req/s | 1.17 s | 2.47 s | 128/128 成功 |
| Python | 35.99 req/s | 36.07 req/s | 1.63 s | 3.27 s | 128/128 成功 |

聊天突发吞吐提高 1.0%，持续吞吐只下降 0.8%，流式吞吐下降 3.5%。处理能力没有随负载翻倍而下降；P95 大约增长到 2.0–2.4 倍，符合固定服务能力下排队人数翻倍的预期。

快速模型的实际上游并发峰值由 8 上升到 13，没有超过默认 16。服务内存峰值由 57.96 MB 上升到 58.75 MB，仅增加 0.79 MB。

## 750 ms 慢模型

| 阶段 | 64 人吞吐 | 128 人吞吐 | 64 人 P95 | 128 人 P95 | 结果 |
|---|---:|---:|---:|---:|---|
| 学生加入 | 96.47 req/s | 90.46 req/s | 0.57 s | 1.27 s | 128/128 成功 |
| 健康检查 | 88.99 req/s | 78.68 req/s | 1.84 s | 4.77 s | 1,024/1,024 成功 |
| 聊天突发 | 18.32 req/s | 18.97 req/s | 3.30 s | 6.49 s | 128/128 成功 |
| 持续聊天 | 19.59 req/s | 19.59 req/s | 4.71 s | 7.00 s | 512/512 成功 |
| 流式聊天 | 16.91 req/s | 18.60 req/s | 3.53 s | 6.49 s | 128/128 成功 |
| Python | 32.01 req/s | 35.32 req/s | 1.81 s | 3.09 s | 128/128 成功 |

双倍负载下聊天突发吞吐提高 3.5%，持续吞吐完全相同，流式吞吐提高 10.0%。慢模型能够持续用满 16 个上游槽位。聊天突发 P95 接近翻倍，持续聊天 P95 增长 48.7%，没有出现非线性恶化。

服务内存峰值由 59.79 MB 上升到 65.52 MB，增加 5.73 MB。对 32 GB 教师机而言仍很低。

## 数据完整性

| 指标 | 64 人 | 128 人 |
|---|---:|---:|
| 模型阶段上游请求 | 384 | 768 |
| 流式上游请求 | 64 | 128 |
| SQLite 入队/写入 | 839/839 | 1,671/1,671 |
| SQLite 最终排队 | 0 | 0 |
| SQLite 丢弃 | 0 | 0 |
| SQLite 写入失败 | 0 | 0 |

双倍测试的固定功能检查部分不翻倍，因此写入总数为 1,671，而不是简单的 1,678。学生会话 ID 和学生令牌在 128 名学生间保持唯一，课堂结束后旧链接和旧会话仍全部失效。

## 压测器连接修正

慢模型的前两次 128 人尝试分别出现少量客户端 `ReadError`。服务端没有异常日志，错误集中在长时间持续阶段。进一步记录异常类型后确认，压测客户端与 Uvicorn 使用相近的默认 keep-alive 过期时间，单机连接池会在服务端关闭连接的同时尝试复用。

将压测客户端 `keepalive_expiry` 调整为 2 秒，使客户端先于服务端淘汰空闲连接后，最终轮所有请求成功。该修正只作用于本地压测工具，没有修改 EduGate 产品连接逻辑。真实浏览器会自行管理和重建空闲连接。

## 判断

1. 默认 16 路可以稳定承载 64 人课堂，并能在 128 人双倍压力下保持吞吐和数据完整性。
2. 128 人同时提问时，等待时间会因固定 16 路上游并发而增长；这属于排队容量，不是本地服务崩溃。
3. 继续把默认值提高到 32 可以降低 128 人等待，但会增加通用上游的瞬时压力。基于此前并发基准，默认 16 仍是更合适的通用值。
4. Python 默认按 64 人课堂设计；128 个任务可以稳定完成，但本报告没有把默认候位队列扩展到 128。
