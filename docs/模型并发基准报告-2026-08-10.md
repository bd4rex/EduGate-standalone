# 模型并发基准报告

**中文** · [English](Model-Concurrency-Benchmark-2026-08-10.md) · [返回项目首页](../README.md)

测试日期：2026-08-10

## 结论

EduGate 单机课堂版将 `MODEL_MAX_CONCURRENCY` 默认值从 4 调整为 **16**，高级设置仍允许 1–32。

- 4 路无法满足 64 人同时提问，慢响应模型的 P95 接近 13 秒。
- 8 路是快速模型的性能拐点，但慢响应模型仍有明显排队。
- 16 路能兼顾快速和慢速模型；对 64 人课堂相当于最多四批进入上游。
- 32 路是性能优先档。相对 16 路，慢模型持续吞吐提高 47%，但并发槽位增加 100%，持续请求 P95 只降低 9.3%，单位并发效率下降约 26.5%。

因此 16 路是当前教师机、64 人课堂和通用上游兼容性之间的性价比平衡点。已确认上游允许高并发且更看重最低等待时间时，可以手动改为 32；额度不明确的其他厂商建议先用 8。

## 测试环境

- Windows 10.0.19045
- Intel Core i7-8700，12 个逻辑处理器
- 31.83 GB 物理内存
- EduGate 与伪模型均运行在本机回环网络
- Python 执行池固定 4 路，SQLite 使用有界队列和批量写线程
- 课堂记录和技术请求日志均开启

没有使用真实 API Key，不产生模型费用。伪 OpenAI 兼容模型分别模拟 75 ms 快速完整响应和 750 ms 较慢完整响应，不生成真实 token。

## 测试负载

每个并发档位均使用全新数据目录并重启 EduGate，执行：

1. 34 项功能检查，包括登录、模型配置、知识库、课堂生命周期、备份和旧会话失效。
2. 64 名学生同时加入。
3. 512 次健康检查，64 路客户端并发。
4. 64 次普通聊天突发请求。
5. 256 次普通聊天持续请求，客户端并发 64。
6. 64 次流式聊天请求。
7. 64 个 Python 任务。

每轮模型阶段共 384 次上游请求。每轮最终产生 386 条技术请求日志和 453 条课堂互动，共 839 个 SQLite 异步写入项。

| 16 | 8 | 55.24 req/s | 1.04 s | 52.25 req/s | 2.66 s | 48.71 req/s | 1.17 s | 57.96 MB |

快速模型在 8 路后进入约 56–61 req/s 的本地平台区。将配置从 8 提升到 32，持续吞吐只增加 1.7%，实际上游峰值仍只有 9。16 路不会带来额外资源压力，但快速模型本身不需要占满 16 路。

同机直接访问 75 ms 伪模型的对照为 88.87 req/s、P95 0.63 秒。经过 EduGate 还要完成身份、上下文、知识库策略、限流和记录，因此不会等同于裸模型吞吐。

## 750 ms 慢模型

| 配置并发 | 实际上游峰值 | 突发吞吐 | 突发 P95 | 持续吞吐 | 持续 P50 | 持续 P95 | 流式吞吐 | 流式 P95 | 内存峰值 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 4 | 4 | 5.03 req/s | 12.60 s | 5.11 req/s | 12.37 s | 12.60 s | 4.94 req/s | 12.81 s | 59.05 MB |
| 8 | 8 | 9.79 req/s | 6.42 s | 10.01 req/s | 6.25 s | 6.54 s | 9.49 req/s | 6.57 s | 58.97 MB |
| 16 | 16 | 18.32 req/s | 3.30 s | 19.59 req/s | 3.11 s | 4.71 s | 16.91 req/s | 3.53 s | 59.79 MB |
| 32 | 32 | 29.11 req/s | 2.08 s | 28.80 req/s | 1.65 s | 4.27 s | 22.88 req/s | 2.61 s | 61.17 MB |

慢模型能够用满配置槽位。16 路相对 8 路：

- 突发吞吐提高 87.1%，突发 P95 降低 48.7%。
- 持续吞吐提高 95.7%，持续 P95 降低 28.1%。
- 流式吞吐提高 78.2%，流式 P95 降低 46.2%。

32 路相对 16 路仍更快，但收益开始低于槽位增长：持续吞吐提高 47.0%，持续 P95 仅降低 9.3%，而允许的上游并发翻倍。内存只增加约 1.38 MB，本地资源不是限制；主要代价是更高的上游瞬时压力和对不同模型厂商额度的要求。

## 正确性

- 所有正式档位均为 34/34 项功能检查通过。
- 所有压力请求均成功，没有 429、500、连接失败或 SQLite locked。
- 每轮 839/839 个数据库项全部写入，排队最终归零。
- 所有轮次 `dropped=0`、`failed=0`、`last_error=null`。
- 实际上游峰值从未超过该轮配置值。

## 上游额度

截至测试日期，[DeepSeek 官方限速说明](https://api-docs.deepseek.com/zh-cn/quick_start/rate_limit)列出的账号并发上限为：`deepseek-v4-pro` 500、`deepseek-v4-flash` 2500，超过额度返回 HTTP 429。16 路远低于当前默认 DeepSeek 模型的官方额度。

OpenAI 兼容并不代表各模型厂商具有相同额度。使用其他上游时，应把 EduGate 并发设置为不高于账号实际并发上限；遇到 429 时先降到 8，而不是继续提高。

## 建议配置

| 场景 | 建议值 |
|---|---:|
| 额度未知、先保证兼容 | 8 |
| 64 人普通课堂、当前默认 | **16** |
| 已确认上游额度充足，性能优先 | 32 |
| 厂商明确限制为 N | `min(N, 16)` 起步 |

设置位于“系统 → 高级设置 → 模型最大并发”，修改后需要重启服务。并发数不会改变 token 单价，但更高并发会把相同请求更集中地发送给上游。

## 局限

- 伪模型只有固定等待时间，不代表真实模型的首 token、生成速度、网络抖动和服务端排队。
- 本报告验证的是当前教师电脑和 EduGate 本地路径，不承诺其他电脑具有相同吞吐。
- 真实课堂的问题长度和输出长度不同；上线前仍应以所用模型的小规模真实 API 测试确认 429 和延迟。
- 原始 JSON 和隔离数据库保存在本机 `artifacts/model-concurrency-2026-08-10`，不提交包含运行数据的目录。
